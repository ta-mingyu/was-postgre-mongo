## 1. Connection Pool 기준선 (1/4 vs 1/10)

조언해주신 1/4 기준선과 당사가 독자적으로 설정한 1/10 수준(인스턴스당 20~30)을
비교 검토한 결과, 당사 기준이 안정적 범위에 있음을 확인하였습니다.
다만 부하 테스트 단계에서 병목 지점에 따라 조정하는 방향은 동일하게 적용할 예정입니다.

한 가지 당사 내부적으로 논의 중인 사항에 대해 추가 조언을 구하고 싶습니다.

> 부하 테스트에서 병목이 WAS->DB 구간이 아닌 DB 내부(Lock, I/O)에서 발생하는 경우,
> 커넥션 풀을 늘리는 것이 아니라 DB 스펙을 올리거나 Read Replica를 확장하는 방향으로
> 접근하는 것이 맞는지요?
>
> 즉, "풀 사이즈 증설"과 "DB 수평 확장"의 분기 기준에 대해
> 실무 경험에서의 판단 근거가 있으신지 궁금합니다.

## 2. 코어 정렬

고객사마다 천차만별이라는 점을 참고하였습니다.
당사 가이드에서는 코어 배정 비율에 대한 고정 공식은 제외하고,
"DB 계층에 가장 높은 코어를 배정한다"는 원칙만 명시하겠습니다.

## 3. 대용량 실무 사례 참고

공유해주신 24개 시스템(JBoss EAP7 + EDB Master/Slave 6대) 구축 사례는
당사 DB 가이드라인 작성 시 참고 자료로 활용하겠습니다.

당사 현금정보계팀(7개 컨테이너)의 경우, 당사 분석 결과 maxPoolSize 15 x 7 = 105개를
제안한 상태이며, 이 수치가 안정적 범위에 있다고 당사에서 판단하고 있습니다.
다만 실제 트래픽 패턴(야간 피크 등)에 따라서는 증설이 필요할 수 있으므로,
해당 팀의 실제 트래픽 데이터를 수집한 후 최종 판단하겠습니다.

## 4. G1GC 적용 임계점에 대한 당사 분석 및 추가 조언 요청

공유해주신 Oracle 공식 문서와 G1GC Region 분할 방식을 참고로 하여,
당사 다중 인스턴스 환경에서 G1GC 적합성을 독자적으로 분석하였습니다.

```
당사 다중 인스턴스 분할 구조에서의 G1GC Region 분석:

  4GB 호스트  -> 인스턴스당 Heap 2,048m -> G1 Region ~1MB  (오버헤드 우려)
  8GB 호스트  -> 인스턴스당 Heap 2,560m -> G1 Region ~1MB  (오버헤드 우려)
  16GB 호스트 -> 인스턴스당 Heap 3,584m -> G1 Region ~2MB  (경계)
  32GB 호스트 -> 인스턴스당 Heap 5,120m -> G1 Region ~2.5MB (경계)

  당사 분석 결론: Heap ~6GB 이상에서 G1GC 유효 구간 진입 (Region ~3MB+)
```

이 분석을 바탕으로, 당사 다중 인스턴스 구조에서는 인스턴스당 Heap이 2~5GB 수준이므로
ParallelGC를 기본으로 가져가는 방향을 검토 중입니다.

이 방향성에 대해 추가 조언이 있으시면 부탁드립니다.

> 1. Heap 2~5GB 수준의 다중 인스턴스 환경에서 ParallelGC를 기본으로 채택하는 것이
>    당사 분석과 일치하는지요?
>
> 2. 아니면 G1GC의 Region 크기를 명시적으로 조정(예: -XX:G1HeapRegionSize=4m)
>    하여 G1GC를 유지하는 방안도 실무에서 고려해 볼 만한지요?
>
> 3. 당사 가이드를 "Heap 6GB 미만 = ParallelGC, 6GB 이상 = G1GC" 구조로
>    단순화하여 명시하면, 실무적으로 무리가 없는지요?
