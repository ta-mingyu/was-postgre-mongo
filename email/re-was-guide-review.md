## 1. 선형 비례(1/4) Anti-Pattern 검토 결과에 대한 동의 및 반영

말씀하신 대로, 저희 역시 1/4을 "모든 계층에 동일하게 적용하는 공식"이 아닌
"초기 설정 시 참조하는 기준선(Baseline)"으로 이해하고 있었습니다.

다만 당사 가이드라인 작성 과정에서, 이 기준선을 선형 공식처럼 오버스펙까지
수치화하여 기재한 부분이 있었습니다. 해당 내용은 Anti-Pattern 섹션으로
격리하였고, 실무 적용안에서는 아래와 같이 보정하였습니다.

- **WAS maxThreads**: CPU 코어 수 기반 산정, 실제 상한 500 (대부분 200 권장)
- **DB maxPoolSize**: HikariCP 공식(`DB_Cores * 2 + N`) 기반, 인스턴스당 20~30
- **스케일 아웃 원칙**: 처리량 증설 시 단일 인스턴스의 풀/스레드를 늘리지 않고
  인스턴스 수를 확장하는 구조로 설계

이 내용은 말씀하신 "많은 스레드와 커넥션이 필요하면 스케일아웃이 효과적"이라는
조언과 일치하는 방향으로 반영되었습니다.

## 2. 코어 배정 철학에 대한 정렬

"Web, WAS, RDB 코어수를 다르게 배정하며, RDB에 가장 높게 배정한다"는 점은
당사에서도 동의합니다. 현재 당사 인프라에서도 DB 서버에 WAS 대비 더 많은
코어와 메모리를 할당하고 있는 구조입니다.

한 가지 추가로 여쭙고 싶은 것이 있습니다.

> 대용량 시스템 구축 경험에서, Web / WAS / RDB 각 계층의 **코어 배정 비율**에
> 대해 일반적인 가이드라인이 있으신지요?
>
> 예를 들어, 전체 코어 자원이 정해졌을 때 각 계층에 어떤 비율로 배정하는 것이
> 벤치마크상 효율적이었는지, 참고할 수 있는 사례가 있으면 공유 부탁드립니다.

이 부분은 당사 표준 가이드라인의 다음 버전에 코어 배정 섹션을 추가하는 데
활용하겠습니다.

## 3. 기준선(1/4)의 실무 적용 방식 확인

말씀하신 "그 정도 선에서 일단 잡고 퍼포먼스 테스트 시 조정"이라는 접근 방식을
아래와 같이 이해하였습니다. 확인 부탁드립니다.

```
1단계: 1/4 비율을 초기 설정값의 기준선으로 참조
2단계: 해당 값으로 퍼포먼스 테스트 수행
3단계: 병목 지점(컨텍스트 스위칭, DB Lock 경합 등) 식별 후 조정
4단계: 조정 완료된 값을 해당 환경의 표준으로 확정
```

이 이해가 맞다면, 당사 가이드라인에 "초기 기준선 산정 -> 부하 테스트 ->
조정 -> 표준값 확정" 프로세스를 명시하겠습니다.

## 4. 기타 논의 사항

당사 현금정보계팀의 경우 7개 컨테이너가 단일 DB를 공유하는 구조입니다.
인스턴스당 maxPoolSize=15로 설정 시 총 105개 커넥션이 발생하는데,
공유 DB 환경에서 이 수준이 적정한지, 혹은 컨테이너당 더 축소해야 하는지에
대한 의견도 부탁드립니다.
